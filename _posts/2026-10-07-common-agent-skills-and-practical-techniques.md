使用编程助手维护一个小项目时，困难往往分布在不同阶段：需求还没有明确，模型就开始写代码；业务术语没有统一，文件和变量的命名逐渐分散；页面已经生成，却没有检查窄屏和键盘操作；准备换一个会话继续工作，又要重新解释前面的决定。Agent Skills 可以把这些阶段中反复使用的方法整理成流程，帮助模型按相对稳定的步骤工作。

本文介绍八个代表性技能：`grilling`、`grill-with-docs`、`domain-modeling`、`codebase-design`、`improve-codebase-architecture`、`frontend-design`、`pdf` 和 `handoff`，并补充 Word、表格与演示文稿技能的选择方法。选材来自实际检查过的安装副本和作者资料；“常用”表示这些任务在个人开发中经常出现，不表示经过统计的热度排名。

**阅读前提**：能阅读 Markdown，理解基本目录与文件操作；运行配套项目需要 Python 3.10 或以上版本及现代浏览器。Skill 调用练习需要支持该技能的宿主和相应工具。安装、来源审查和调用评估的完整方法见[Agent Skills 的使用与评估]({% post_url 2026-10-05-agent-skills-usage-and-evaluation %})，本文集中讲具体技能的用途与使用技巧。

**实践与证据范围**：课程名称、资料记录、需求答复和参考产物均为教学模拟。配套程序用于生成可检查的页面和统计结果，不会调用模型或安装 Skill。本文核对了技能内容和官方资料，实际运行范围见[验证记录]({{ '/assets/examples/agent-skills-practice/VALIDATION.md' | relative_url }})；提示词、架构建议和交接样例不能作为原生 Skill 触发率或模型效果的实测证据。资料核对日期为 **2026-10-07**。

## 1. Skill 的组成与调用方式

### 流程、规则与工具

一次请求说明当前要做的事，Skill 保存一类任务的做法，项目规则规定当前项目的工作边界，工具负责实际读取、搜索、执行和写入。它们可以共同参与同一个任务，但需要分别检查。

| 组成 | 本文案例中的职责 | 检查重点 |
| --- | --- | --- |
| 本次请求 | 改进课程资料列表，输出检查记录 | 目标、输入、输出是否明确 |
| Skill | 安排需求追问、设计审查或交接过程 | 流程是否适合当前问题 |
| 项目规则 | 保留输入，限制修改范围 | 操作是否符合项目约束 |
| 工具 | 读取 CSV、修改代码、预览页面 | 能力是否可用，操作是否完成 |

Skill 目录以 `SKILL.md` 为入口，也可以包含脚本、参考资料和模板。名称与描述帮助宿主发现适用技能，正文和资源进一步规定流程。检查时应顺着引用阅读配套文件；只看到一个名称，还不能知道它会读写什么。[Agent Skills 规范](https://agentskills.io/specification)

### 显式调用与自然匹配

显式调用适合希望采用某个明确流程的任务；自然匹配适合让宿主根据任务描述选择技能。正式练习建议先使用显式调用，方便确认实际采用的副本，再观察自然匹配。

Codex CLI 与 IDE 扩展的官方说明提供 `/skills` 和 `$` 提及入口，ChatGPT 的技能选择使用 `@`；界面、产品和版本不同，具体入口也可能不同。在支持 `$` 提及的 Codex 输入框中，可以输入 `$frontend-design` 并从候选列表选择，随后补充任务要求。这里的 `$frontend-design` 是**提交给助手的请求内容**，不是在 PowerShell 或 Bash 中执行的命令。[官方技能用法](https://learn.chatgpt.com/docs/build-skills)

作者的 Claude Code 示例可能使用 `/skill-name`，不能直接把它当作所有宿主的调用语法。同样，本文检查的部分副本包含 `disable-model-invocation: true`；这是副本中的调用标记，实际解释仍取决于宿主。Codex 官方还提供 `agents/openai.yaml` 中的 `policy.allow_implicit_invocation`。不要把不同宿主的配置字段当作完全等价的通用规范。

“已安装”“本轮可见”“被选择”“实际执行”是四个不同状态。模型声称使用了某个技能时，可以核对它读取的入口、采用的关键步骤和实际产物；宿主已经注入正文时，日志也可能没有额外读取事件，证据不足的状态应保留为未知。

### 练习项目与初始状态

配套项目是一个没有框架依赖的课程资料目录。它包含六条模拟记录、一个 Python 生成程序，以及用于筛选列表的原生 JavaScript。下载[练习包]({{ '/assets/examples/agent-skills-practice/agent-skills-practice.zip' | relative_url }})后解压，进入其中的 `project` 目录；源文件和使用说明也见[配套入口]({{ '/assets/examples/agent-skills-practice/README.md' | relative_url }})。

```text
project/
├── data/materials.csv       # 六条模拟资料，练习中保留原文件
├── docs/brief.md            # 需求草案，包含待确认问题
├── src/catalog.py          # 读取、校验与分类统计
├── src/app.js              # 页面筛选与结果数量
├── src/style.css           # 页面及打印样式
├── prepare.py              # 生成一个新的产物目录
└── README.md
```

在 `project` 目录执行以下命令。PowerShell 与 Bash 的命令相同；Linux、macOS 若没有 `python` 别名，可使用 `python3`。先确认 `python --version` 符合版本要求。

```bash
python prepare.py --output output/run-01
python -m http.server 8766 --bind 127.0.0.1 --directory output/run-01
```

第一条命令校验输入并生成 `index.html`、`summary.csv`、`summary.json` 和 `report.html`，同时复制页面脚本与样式；第二条命令仅把这个产物目录用于本机预览。打开终端显示的地址，例如 `http://127.0.0.1:8766/`，应看到六条资料。端口被占用时改用另一个端口，并同步修改浏览器地址；结束预览在终端按 `Ctrl+C`。

程序拒绝覆盖已有产物目录。重复实验使用 `output/run-02` 等新目录，便于保留前一次结果。修改源文件后，需要重新生成并预览新的产物，旧目录不会自动更新。配套程序的行为由代码决定，运行它不等于调用了本文介绍的任何 Skill。

## 2. 需求澄清与决策记录

### grilling 的问题组织

`grilling` 适合需求、方案或决策仍然模糊的阶段。它把问题之间的依赖关系组织起来：已经解决的问题使后续问题有了前提，尚未确定的决定则继续等待讨论。[grilling 源文件](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)

本例草案只有“方便按课程查找资料”，没有明确资料来自哪里、分类与标签的关系，以及是否需要登录。此时直接要求生成完整应用，会让模型用自己的假设补齐这些决定。下面的请求把追问范围固定在已有项目上。

<!-- prompt:P01-grilling -->
```text
使用 grilling 帮我明确课程资料管理项目的需求。
当前工作目录是解压后的 project。先读取 docs/brief.md 和 data/materials.csv。
用户是个人学习者，本次范围是本机资料清单浏览，不接入账号或云端服务。
请区分资料中的事实、我的既定决定和仍需我回答的问题。
已能从文件查到的事实请自行检查；决定问题按前置关系分轮提出，附上建议理由。
先讨论范围、课程与分类的关系、关键词匹配和缺失日期的展示。
这一阶段只读取文件和讨论，不修改项目。等我明确结束需求讨论，再进入下一阶段。
```

这一轮合理的问题包括：一条资料能属于几个课程；分类是否只有一个；标签能否有多个；关键词是否匹配标题、课程与标签；没有更新日期的资料怎样展示。CSV 中现有几条记录、课程名称有哪些，则可以直接读取，不必让用户重新抄写。

练习采用以下**教学决定**作为后续阶段的输入：每条资料属于一个课程和一个分类，标签允许多个；关键词匹配标题、课程与标签，采用不区分大小写的子串匹配；分类和关键词同时生效；空日期显示“未提供”；本次只生成浏览和统计结果，不编辑原始 CSV。

验收需求澄清时，检查每个关键选择是否有答复、理由和范围，而不是只数提出了多少问题。简单且已经明确的任务不必开展完整访谈。实际讨论中若某轮出现过多问题，可以要求先处理影响范围最大的两三项，并说明剩余问题何时继续。

### grill-with-docs 的文档协同

`grill-with-docs` 在需求追问的同时采用领域建模方法，使确认后的术语和重要决定进入持久文档。本文检查的入口很短，它引用 `grilling` 和 `domain-modeling`；因此完整流程依赖这些配套技能，而不是只靠入口的几行文字。[grill-with-docs 源文件](https://github.com/mattpocock/skills/blob/main/skills/engineering/grill-with-docs/SKILL.md)

<!-- prompt:P02-grill-with-docs -->
```text
使用 grill-with-docs 继续课程资料管理项目的需求讨论。
读取 docs/brief.md、data/materials.csv 和现有术语或决策文档；缺少的文件如实记录。
沿用已经确认的单课程、单分类、多标签、组合筛选和空日期规则。
请核对所需的 grilling、domain-modeling 是否可用；缺少时先说明影响。
允许在当前 project 中维护 GLOSSARY.md 和 docs/adr/，不修改数据和程序。
术语确认后记录业务含义；只有影响长期维护且存在真实取舍的决定才建立 ADR。
输出本轮确认项、修改的文档路径和仍未解决的问题。
```

两者的选择取决于产物需要：临时讨论、想法检验可以先用 `grilling`；项目将持续迭代，并且术语或决定值得保留时，适合 `grill-with-docs`。同一需求不需要把两套完整访谈连续重复一遍。第二个请求是替代方案，也可以用于前一轮讨论后的文档整理。

## 3. 领域建模与代码架构

### domain-modeling 的术语边界

`domain-modeling` 处理业务语言。它帮助澄清模糊概念，并把已确定的含义记录在术语表中；需要解释重要取舍时，再使用架构决策记录（ADR）。术语表回答“概念是什么意思”，ADR 说明“为什么采用这个决定”。[domain-modeling 源文件](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/SKILL.md)

例如，`course` 表示资料所属的教学科目，`category` 表示资料形式，`tags` 表示检索主题。把“Python 程序设计”当作分类，或者把“讲义”当作课程，会让统计、筛选和界面命名逐渐失去一致性。

<!-- prompt:P03-domain-modeling -->
```text
使用 domain-modeling 核对课程资料管理项目的业务术语。
读取 docs/brief.md、data/materials.csv、src/catalog.py、src/app.js 和现有 GLOSSARY.md。
重点核对资料、课程、分类、标签及未知更新日期的含义和关系。
允许维护 GLOSSARY.md；发现业务决定值得记录时，先说明真实取舍再提出 ADR 建议。
术语表只记录业务概念，不把函数名、CSS 选择器或实现步骤写进定义。
输出术语表改动，并列出代码与既定需求不一致的位置；不修改程序或输入数据。
```

一个可检查的结果应能说明：资料是清单中的一条记录，记录由唯一 ID 标识；一条资料属于一个课程和一个分类，可以有零个或多个标签；更新日期为空表示未提供，不能自动补成当前日期。术语表需要与数据和既定需求一致，不追求词条数量。

### codebase-design 的接口分析

`codebase-design` 提供分析模块设计的共同语言。重点是调用者需要知道多少规则，以及模块能够隐藏多少复杂度；模块内部代码较长，并不自动意味着接口设计较好。[codebase-design 源文件](https://github.com/mattpocock/skills/blob/main/skills/engineering/codebase-design/SKILL.md)

本例的 `load_materials(path)` 统一负责读取、字段校验、ID 唯一性、日期解释和标签拆分，生成程序只接收规范化记录。相比让页面生成、统计和报告导出各自解释一次 CSV，这个接口能把共同规则集中到一处。但这个小项目也不需要预先增加数据库适配层或插件系统。

<!-- prompt:P04-codebase-design -->
```text
使用 codebase-design 只读分析课程资料管理项目。
读取 prepare.py、src/catalog.py 和 src/app.js；沿用已确认的业务术语。
分析读取校验、分类统计、HTML 生成和页面筛选各自向调用者暴露的规则。
请给出一个值得考虑的设计改进，说明涉及文件、重复知识、接口变化及验证方法。
若现有组织已足够支撑六条记录的练习，请说明哪些抽象可以暂缓。
不要只按文件大小判断设计，也不要为了新增层次拆分简单函数。
只提供分析，不修改代码。
```

验收时，应能沿着建议找到具体代码和重复规则。例如，一个建议若声称“日期解释分散”，就需要指出实际位置；只有口号式的“解耦”“分层”还不足以判断收益。对一个改进可以追问：去掉这个模块后，共同规则会重新分散到哪些调用者；测试能否通过其公开接口覆盖真实行为。

### improve-codebase-architecture 的候选调查

`improve-codebase-architecture` 更接近一套调查流程：确定关注范围，检查代码，形成候选改进报告，再围绕选中的候选继续讨论。本文检查的版本会借助其他技能，并安排子代理探索；它还在临时 HTML 报告中使用 CDN 资源。这些依赖需要在采用流程前确认。[improve-codebase-architecture 源文件](https://github.com/mattpocock/skills/blob/main/skills/engineering/improve-codebase-architecture/SKILL.md)

<!-- prompt:P05-architecture -->
```text
使用 improve-codebase-architecture 调查课程资料管理项目的维护问题。
关注 prepare.py 中页面生成与报告生成的关系，以及未来增加资料形式时的改动范围。
先读取业务术语、现有 ADR 和相关代码；项目没有 Git 历史时如实说明，以指定范围开展调查。
先核对所需技能、子代理和报告展示能力。能力不足时说明哪一步无法执行，不声称完成完整流程。
调查阶段只读取项目。报告保存到临时目录，列出候选、涉及文件、问题依据、预期收益和不确定性。
若报告依赖 CDN，说明离线浏览的限制；关键结论应保留为可读文字。
完成候选报告后暂停实施，由我选择需要进一步讨论的候选。
```

这个请求授权的是调查和临时报告，不代表允许直接重构整个项目。报告之后还需要选定候选、确认约束，再单独进入实现。推荐强度也应有依据：观察到的重复规则、经常修改的路径和测试困难，比对未来规模的想象更有说服力。

三个技能之间可以这样区分：`domain-modeling` 统一业务含义，`codebase-design` 分析模块接口，`improve-codebase-architecture` 组织代码调查和候选选择。需求只涉及一个明确函数时，直接使用接口分析通常就够了。

## 4. 前端设计与页面验证

### frontend-design 的设计过程

`frontend-design` 适合新页面设计或已有界面改进。本文核对的版本强调围绕主题做出视觉选择，并经历方案、实现和检查的过程。设计输入越具体，越容易判断最终页面是否服务于实际内容。[frontend-design 源文件](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)

本例最重要的内容是资料标题、课程、分类和可用状态，检索入口应便于找到；介绍区、配色和装饰都应围绕这些内容安排。六条模拟记录已经足够检查长标题、标签、缺失日期与空结果，没有必要再编造访问量或用户评价来填充页面。

<!-- prompt:P06-frontend-design -->
```text
使用 frontend-design 改进课程资料管理页面。
读取 docs/brief.md、src/style.css、src/app.js 和 prepare.py 中的页面结构，先预览现有产物。
用户是个人学习者，重点任务是按课程、分类和关键词找到资料。
保持原生 HTML、CSS、JavaScript 和现有生成方式；保留六条输入记录及其含义。
采用系统字体，不加载外部字体、图片或 CDN。先提出信息层级、配色与布局方案，暂不改代码。
方案确认后的实现范围是页面模板、src/style.css 和 src/app.js，不修改 data/materials.csv。
页面需要在 390px 和 1440px 宽度下可读，支持键盘、可见焦点、空结果和缺失日期提示。
实现后生成新的产物目录，检查分类与关键词组合筛选，并提供实际桌面、移动端截图。
无法完成的浏览器检查请单独记录。
```

系统字体、技术栈和修改范围都是当前项目的明确约束；设计技能的通用建议需要在这些约束内执行。使用参考页面时，应说明借鉴的是信息层级、留白还是交互位置，避免只给一个网址让模型猜测。

### 功能与视觉验收

先以初始页面进行以下检查，再在改进后的新产物上复查。

| 操作 | 本例应有结果 |
| --- | --- |
| 初次打开 | 显示六条资料，MAT-05 与 MAT-06 的日期为“未提供” |
| 关键词“文件” | 显示 MAT-01、MAT-02 |
| 分类“讲义”与关键词“文件” | 只显示 MAT-01 |
| 关键词“SQL” | 显示 MAT-04、MAT-05 |
| 关键词“没有这条资料” | 显示零条及明确的空结果说明 |
| 清除筛选 | 恢复六条资料 |
| 关闭 JavaScript | 基础资料列表仍可阅读，筛选入口隐藏 |

视觉验收应查看实际渲染页面：窄屏不能出现整页横向滚动，长标题和标签不能遮挡操作；键盘能够到达筛选控件和链接，焦点可见；空结果要解释当前状态并提供恢复入口。截图说明布局表现，交互检查说明行为，两者相互补充。

普通单页练习不一定需要复杂动画。先处理信息层级和读取效率，再判断动效是否有具体用途，通常比笼统要求“高级感”更有效。

## 5. 文档处理与产物交付

### pdf 的读取与检查

`pdf` 适合 PDF 内容提取、生成和版面核验。名字相同的技能也可能来自不同发行包；本文检查到独立副本和插件副本均采用提取与渲染结合的流程，使用时仍应确认实际入口与依赖。[OpenAI PDF 技能示例](https://github.com/openai/skills/tree/main/skills/.curated/pdf)

对于输入文件，先判断它包含可提取文本，还是需要 OCR 的扫描图像。提取文本方便核对记录，渲染页面有助于发现截断、重叠、字符缺失和表格错位。OCR 的结果还需要返回页面核对，不能把识别成功等同于内容准确。

本文的文档练习从已有 CSV 出发。运行生成程序后，`summary.json` 应包含总数 6、未提供日期 2、分类计数“讲义 3、示例代码 2、练习 1”；`summary.csv` 保存同一统计口径。`report.html` 是可以浏览和打印的参考报告，默认按完整输入统计，不随页面筛选改变。

<!-- prompt:P07-pdf -->
```text
使用 pdf 为课程资料管理项目生成一页 A4 PDF 报告。
读取 data/materials.csv、docs/brief.md、output/run-01/summary.json 和 output/run-01/report.html。
先独立核对六条记录与分类统计，再参考 report.html 的信息结构。
输出总数、各分类数量、两条未提供更新日期的资料 ID，以及全部六条资料的简表。
空日期写“未提供”，不补日期；明确课程与记录均为教学模拟。
使用可显示中文的字体，检查字体嵌入、提取文字和实际页面渲染。
输出到新目录 output/pdf-run-01，不覆盖源文件或已有产物。
记录实际工具、页数和版面检查结果；缺少生成或渲染能力时说明未完成项。
```

配套包提供 HTML 报告，不预置声称由 `pdf` Skill 生成的 PDF。读者可以执行上述原生调用，也可以用浏览器打印功能保存 PDF；后一种操作应记录为浏览器导出。两种分支都要确认实际页数和文字显示，不能用 HTML 预览代替最终 PDF 检查。

### Word、表格与演示文稿

输出格式应根据用途选择，技能名称以当前宿主可见清单为准。

| 技能类别 | 适用产物 | 关键验收 |
| --- | --- | --- |
| Documents | 需要继续编辑的 Word 报告 | 标题层级、表格结构、分页、样式及渲染 |
| Spreadsheets | 需要筛选、公式或图表的资料统计 | 行列含义、数据类型、公式与重算结果 |
| Presentations | 向同学介绍整理方法的短演示 | 每页主题、信息密度、图表与页面渲染 |
| PDF | 需要固定版式分发的报告 | 内容、页数、中文字符和最终版面 |

例如，表格任务可要求保留六条原始记录，另建统计工作表；演示文稿可以分成“资料情况—检索方法—待补信息”三页。Word 报告和幻灯片是替代输出分支，练习时不必全部生成。

<!-- prompt:P08-spreadsheets -->
```text
使用当前可用的 Spreadsheets 技能整理课程资料清单。
输入 data/materials.csv，生成新的 output/xlsx-run-01/materials.xlsx。
保留原始记录工作表，字段顺序和六条记录不变；ID 按文本保存，未知日期保持空白。
另建分类统计工作表，写明统计对象是完整清单，分类数量为 3、2、1，总数为 6。
若使用公式，请完成实际重算并核对结果；若使用静态计数，请明确标注。
检查表头、筛选、列宽、长标题和日期展示，不覆盖 CSV 或已有工作簿。
给出文件路径、检查结果和未完成项。
```

文件存在、能够打开、内容正确和版面合格也是不同状态。模型在聊天中排出一张表，并不意味着已经交付可编辑工作簿；工具返回文件路径后，还需要检查那个实际文件。

## 6. 会话交接与上下文整理

### handoff 的交接内容

`handoff` 适合把较长会话压缩成下一位助手可以接手的文档。本文检查的版本默认保存到操作系统临时目录，引用已有材料，并根据下一阶段目标组织内容。[handoff 源文件](https://github.com/mattpocock/skills/blob/main/skills/productivity/handoff/SKILL.md)

交接最有价值的内容通常是：当前目标，已确认的决定，实际修改与文件位置，完成的验证，原始失败，尚未解决的问题，以及下一步。不需要逐句复述整个对话，已经写入项目文档的内容可以通过路径引用。

<!-- prompt:P09-handoff -->
```text
使用 handoff 为课程资料管理项目准备交接文档。
下一会话将处理 PDF 报告导出，当前阶段结束于页面与统计检查。
请核对当前文件和产物目录，区分已有教学基线、我本轮的实际修改和尚未执行的任务。
记录已确认的需求、输入 CSV 的位置、产物路径、实际检查及失败、未验证事项和下一步。
引用现有文档，不复制整份 CSV 或全部对话；删除凭据与个人敏感信息。
保存到操作系统临时目录，告诉我绝对路径和建议下一会话使用的技能。
不要声称已完成未执行的原生 Skill 调用、PDF 导出或线上发布。
```

临时目录可能被系统清理。需要长期保存时，可以在确认内容后复制到自己管理的项目文档目录。换设备时还应同时提供项目文件；一个本机绝对路径本身不会把文件传到另一个环境。

### 接手状态的验证

新会话收到交接材料后，应先读取其中引用的文件，核对输入和产物是否仍存在，再选择下一步。示例请求如下：

```text
请先读取我提供的交接文档，核对它引用的项目文件和实际产物。
用简短文字说明当前目标、确认过的决定和未完成项。
若路径失效或记录与文件不一致，请说明差异；核对完成后再处理 PDF 导出。
```

配套的交接模板把“实际完成”“未执行”“下一步”分别列出。填写检查记录时应写明条件，例如“在 390px 视口检查了列表与空结果”，比“移动端没问题”更容易在下一会话复核。

## 7. 技能组合与常见问题

### 阶段输入与输出

一条可裁剪的流程是：需求澄清，术语整理，设计或架构分析，实现，验证，交接。任务只涉及一个阶段时，直接进入相应阶段即可。

| 阶段 | 可选技能 | 传递给下一阶段的材料 |
| --- | --- | --- |
| 需求澄清 | grilling 或 grill-with-docs | 目标、范围、确认的答复与待定项 |
| 术语整理 | domain-modeling | 术语表和必要的决策记录 |
| 设计分析 | frontend-design、codebase-design 或架构调查 | 选定方案、涉及文件、接口和验收条件 |
| 实现与交付 | 当前任务所需工具与文档技能 | 实际改动、生成产物、失败与限制 |
| 验证 | 浏览器、解析器、渲染器等工具 | 对应输入与产物的检查证据 |
| 会话交接 | handoff | 当前状态、引用路径和下一步 |

组合的关键是让后一阶段读取前一阶段已经确认的产物，而不是重新解释一遍需求。只有阶段结果符合验收条件，才适合继续扩大操作范围。调查报告完成之后，还可以选择暂不实施；交接文档也可以记录这种决定。

### 调用请求的六个要素

通用模板包含技能、目标、材料、范围、产物和验收。提交前替换占位符，并以宿主实际显示的技能名为准。

<!-- prompt:P10-template -->
```text
使用 <当前宿主可见的技能名称> 完成 <具体目标>。
当前工作目录是 <项目目录>，请先读取 <输入文件与相关约束>。
本次允许 <读取或修改范围>，需要保留 <原始资料或已有行为>。
请按照 <已经确认的业务决定或模板> 工作。
输出 <产物类型与新的保存位置>。
验收标准是 <可观察的内容和行为>；记录实际执行、失败与未完成项。
```

“使用某个技能优化一下”只规定了流程名称，没有固定任务。完整请求仍需说明材料在哪里、什么必须保留、结果怎样检查。提示词里指定的目录应真实存在；资源文件路径和任务输入路径也要分别理解。

### 发现、依赖与版本问题

| 现象 | 核对顺序 |
| --- | --- |
| 技能没有出现在候选列表 | 名称与完整目录、宿主作用域、启用状态及列表是否截断 |
| 能看到名字，但任务没有采用它 | 描述是否匹配、显式调用是否被宿主解析、正文是否已提供 |
| 已加载，却无法生成产物 | 工具、依赖、字体、权限、输入路径与实际错误 |
| 复合技能中途停止 | 被引用的技能、子代理或报告展示能力是否齐全 |
| 建议与项目规则冲突 | 明确当前约束，重新限定技能流程与修改范围 |
| 上游示例与本机行为不同 | 对照来源、文件摘要、更新时间和宿主版本 |
| 输出看似完成，实际文件缺失 | 核对实际路径、工具返回值与文件内容 |

官方资料说明，初始技能列表有容量限制，安装较多技能时可能压缩描述或省略部分条目。因此，未出现在某次会话的初始清单中，不足以直接推断卸载或禁用。[官方技能文档](https://learn.chatgpt.com/docs/build-skills)

维护技能时，记录来源地址与实际副本的文件摘要，并顺着入口检查依赖。摘要能帮助确认是否使用了同一个文件，不能证明内容可信，也不能当作 Git 提交号。本文配套的来源记录只用于说明核对对象，不包含个人安装路径和凭据。

## 8. 选择速查、实践练习与参考资料

### 选择速查

| 当前问题 | 优先考虑 | 最小输入 |
| --- | --- | --- |
| 目标与范围仍然模糊 | grilling | 草案、既定决定、约束 |
| 需要边讨论边保存项目语言 | grill-with-docs | 草案、现有术语与文档权限 |
| 同一个业务概念出现多种含义 | domain-modeling | 业务示例、术语表、相关代码 |
| 接口规则复杂或共同规则分散 | codebase-design | 模块代码、调用位置、变化需求 |
| 需要调查多个架构改进机会 | improve-codebase-architecture | 关注范围、术语、ADR、代码及可用能力 |
| 页面信息层级与视觉效果不足 | frontend-design | 真实内容、现有页面、视觉与技术约束 |
| 需要固定版式报告 | pdf | 来源、统计口径、版面和检查要求 |
| 需要换会话继续工作 | handoff | 当前目标、产物、实际验证和下一阶段任务 |

### 扩展技能索引

以下技能在相关任务中有用，本文保留最小入口，具体操作按当前副本和宿主说明核对。

| 技能类别 | 适用场景 | 使用要点 |
| --- | --- | --- |
| openai-docs | 核对 OpenAI 产品或 API 行为 | 指定产品和问题，采用官方资料并保留核对日期 |
| skill-creator | 把稳定重复流程整理成自有技能 | 提供适用与排除任务、输入、输出和验收示例 |
| skill-installer | 安装来源明确的已有技能 | 阅读完整目录，确认依赖和安装目标，安装后核对文件 |
| imagegen | 创建或编辑位图素材 | 说明用途、尺寸倾向、风格和透明背景要求 |
| visualize | 在对话中解释关系或比较方案 | 给出要表达的问题与可交互变量 |
| 浏览器与计算机操作 | 检查实际页面或应用状态 | 使用可用工具，核对真实操作与状态 |
| Sites | 创建、预览和托管 Sites 项目 | 明确使用 Sites，区分本地预览与实际发布 |

技能名称不会自动带来对应工具、账号或服务权限。例如，网页检查需要实际浏览器能力，图片生成需要可用的生成工具，托管还涉及明确的发布操作。先确认当前环境再安排产物，比按名称推断能力更可靠。

### 实践练习

1. **需求澄清**：使用 P01 或 P02 处理草案。验收标准：单课程、单分类、多标签、组合筛选及未知日期都有明确答复；文件中已有的事实没有变成重复追问。
2. **设计与架构**：选择 P04、P05 或 P06 中一个方向。验收标准：分析对应具体文件；实施前范围明确；页面方向完成后有实际桌面和窄屏检查。
3. **文档交付**：使用 P07 或 P08 生成一个实际文件。验收标准：六条记录保留，分类统计为 3、2、1，未提供日期仍为未知；最终文件经过内容和格式检查。
4. **会话交接**：使用 P09，并在新会话核对引用。验收标准：文件可以定位，完成与未执行事项分开，下一阶段能根据交接继续工作。
5. **调用对照**：分别在新会话显式点名技能、只描述同一任务。验收标准：记录可见性、选择与执行证据；结果好坏不能单独用来推断触发是否成功。
